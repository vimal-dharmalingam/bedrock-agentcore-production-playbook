# cdk

Hand-written Python CDK app deploying the calculator agent to AgentCore Runtime -- one
`AWS::BedrockAgentCore::Runtime` resource, built directly from `agentRuntimeArtifact.from_asset()`
so `cdk deploy` builds and pushes the Docker image itself (no separate `docker build`/`docker
push`/`aws ecr create-repository` commands, unlike `manual-container-build`).

Not auto-generated by the `agentcore` CLI -- compare against `02-agentcore-cli`, which is also
CDK-backed but you never write or see the CDK code; here every construct is explicit.

## Files

```
app.py              CDK entry point (what `cdk deploy` actually runs, per cdk.json)
cdk_stack.py          The stack: one Runtime construct + the IAM statement it doesn't auto-grant
cdk.json               Tells the cdk CLI how to run app.py
requirements.txt       CDK TOOL's own deps (aws-cdk-lib, constructs) -- runs on your machine
agent/
  my_calc_agent.py      Same agent code as every other sub-method
  requirements.txt      Agent's RUNTIME deps -- installed into the container
  Dockerfile             Same vendor/ + DOCKER_CONTAINER=1 pattern from manual-container-build
  vendor/                 Pre-fetched arm64 wheels (gitignored, regenerate with the command below)
```

## How to run end to end

```bash
cd 01-agentcore-runtime/cdk

# 1. Pre-fetch arm64 wheels for the agent's dependencies (avoids the QEMU compile-from-source
#    hang documented in manual-container-build's README -- CDK's asset build is real `docker
#    build` under the hood, same risk applies)
cd agent
uv pip install --python-platform aarch64-manylinux2014 --python-version 3.13 --target vendor --only-binary=:all: -r requirements.txt
cd ..

# 2. Install the CDK tool's own dependencies
pip install -r requirements.txt

# 3. Preview the compiled CloudFormation template (also builds the Docker image, since CDK
#    needs the image digest to compute the asset hash -- not just a dry run of YAML)
cdk synth

# 4. Deploy -- builds+pushes the image to a CDK-managed ECR asset repo, creates the execution
#    role, creates the Runtime, all as one CloudFormation stack. Prompts to confirm IAM changes.
cdk deploy

# 5. Invoke (deploy's Outputs section prints the exact AgentRuntimeId to use)
python invoke_cdk_agent.py <AGENT_RUNTIME_ID> "What is 25 * 4?"
```

Safe to rerun `cdk deploy` any time -- it diffs against the deployed stack and only changes
what's different. To tear everything down atomically: `cdk destroy`.

## What's different from calling create_agent_runtime directly

- **Declarative, not imperative.** We describe the desired resource; CloudFormation (via CDK)
  diffs and reconciles, rather than us calling `create_agent_runtime`/`update_agent_runtime`
  ourselves like in `direct-code-zip` and `manual-container-build`.
- **The L2 `Runtime` construct auto-creates the execution role** with most of the permissions
  AgentCore Runtime needs (logs, X-Ray, CloudWatch metrics, workload-identity tokens, ECR pull
  for its own asset repo) -- confirmed by reading the actual synthesized template. Meaningfully
  less hand-written IAM JSON than `manual-container-build`'s ~70-line policy.
- **One thing it does NOT auto-grant: `bedrock:InvokeModel`.** Caught this by reading `cdk
  synth`'s output before deploying, not by hitting AccessDenied after the fact -- added it
  explicitly in `cdk_stack.py` via `runtime.role.add_to_principal_policy(...)`.
- **`cdk destroy` tears down the whole stack atomically** -- role, runtime, CDK's own asset
  repo entry -- instead of writing separate delete calls per resource.

## IAM permissions
No new customer-managed policy needed. `cdk bootstrap` for this account/region was already done
during `02-agentcore-cli` (fixed via the `AgentCoreCdkDeployAccess` policy back then), so this
module reused that plus the existing `BedrockAgentCoreFullAccess`/`BedrockAgentCoreCLIAccess`
grants -- zero new AccessDenied errors during this build.

## Notes / gotchas
- **`cdk synth` really builds the Docker image**, not just YAML, when the stack has a
  `fromAsset()` container artifact -- CDK needs the image digest to compute the asset hash. So
  the QEMU-compile-hang risk from `manual-container-build` applies here too, at `synth` time,
  not just `deploy` time. Do the `vendor/` prefetch before your first `cdk synth`, not after.
- **`cdk deploy` can fail with a Docker daemon connection error** (`open //./pipe/docker_engine:
  The system cannot find the file specified`) if Docker Desktop isn't running -- start it, wait
  for it to fully come up, rerun the same `cdk deploy` command; CDK had already built the
  template, so it just needs the daemon to publish the image asset.
- Runtime name is `calc_agent_cdk` -- check `list_agents.py` alongside the others.
